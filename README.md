# auto-calc

Автоматизация расчёта ущерба по страховым заявкам: от появления заявки в базе
до заполненного расчёта в Audatex.

Проект разбит на четыре независимых блока. Каждый запускается и тестируется
отдельно, а обмен между ними идёт через JSON-файл на заявку. Это даёт паузу и
продолжение с места остановки: упало на шаге C — состояние уже лежит на диске.

| Блок | Что делает | Статус |
|---|---|---|
| A. Робот портала | опрос кнопки «Расчет», открытие заявки, тип (ПВУ/ОСАГО/КАСКО), комментарии, выгрузка карточки в JSON | **чтение работает, селекторы уточняются** |
| B. Распознавание акта | PDF/фото → JSON: детали, замена/ремонт/окраска, н/ч, дефекты эксплуатации | **работает, этот репозиторий** |
| C. Каталог и логика | деталь → каталожный номер, ставки ЕМР, ЛКМ | не начат |
| D. Заполнение Audatex | ввод позиций в AudaPad, ручная пауза при ошибке | не начат |

## Блок A: робот портала

Только чтение и скачивание. В портал ничего не записывает.

Логин руками один раз — пароли в коде не хранятся и скриптом не вводятся.
Браузер поднимается с постоянным профилем в `~/.auto-calc/profile`, сессия
переживает перезапуски.

```bash
python3 -m playwright install chromium
python3 portal_cli.py login            # войти руками в открывшемся браузере
python3 portal_cli.py fetch 1234567    # карточка заявки -> data/out/1234567.json
python3 portal_cli.py watch            # опрос «Расчет» раз в минуту
```

Собирает: марку, модель, год, цвет, СТС/ПТС, владельца, пробег, дату ДТП,
экономический регион, № полиса, № убытка, место аварии, тип заявки и
комментарии, разобранные на дату / автора / текст. `СПБ` в месте аварии
разворачивается в `Санкт-Петербург`.

### Про селекторы

Портал на GWT: имена классов вроде `DABET2D-u-r` из регламента генерируются при
сборке и меняются после каждого обновления портала. Поэтому кнопка «Расчет»
ищется по тексту, а поля карточки — по подписи слева, а не по id. Старый класс
оставлен запасным вариантом.

Разбор списка заявок и кнопки «Расчет» написан вслепую, по кадрам записи —
на живом портале селекторы почти наверняка придётся поправить. Для этого есть

```bash
python3 portal_cli.py dump 1234567
```

Команда кладёт HTML и полноэкранный скриншот страницы в `data/out/` — по ним
селекторы правятся точно, а не угадываются.

## Блок B: распознавание акта

```bash
pip install -r requirements.txt
export ANTHROPIC_API_KEY=sk-ant-...
python3 cli.py "/Users/user/Documents/Акты/createpdf (11).pdf"
```

Сначала полезно посмотреть карту страниц — пакеты приходят смешанные
(акт, ПТС, СТС, фото, заказ-наряд в одном PDF, часть страниц вверх ногами):

```bash
python3 cli.py --map "/path/to/act.pdf"
```

### Как устроено

1. `src/pages.py` — PDF рендерится в PNG постранично, длинная сторона до 1800 px.
2. Каждая страница классифицируется дешёвой моделью: тип страницы и нужный
   поворот. Ни один лист акта не имеет текстового слоя — все PDF это сканы или
   фотографии, поэтому обычный парсер PDF здесь бесполезен.
3. Со страниц типа `act_header` и `act_damages` данные извлекаются моделью
   посильнее через tool-use со строгой схемой (`src/schema.py`), поэтому на
   выходе всегда валидный JSON, а не свободный текст.
4. Всё, что модель не прочитала уверенно, попадает в `needs_manual` — эти
   позиции проверяются руками, а не угадываются.

### Про точность

Формы актов различаются: у НМЦ «ТехЮр Сервис» колонки «Замена / Ремонт /
Окраска», у других бланков «Окраска / Замена / Ремонт, н/ч». Схема общая для
обоих, привязки к координатам ячеек нет — именно поэтому используется
vision-модель, а не шаблонный OCR.

Точность растёт не дообучением модели, а накоплением примеров: каждый
проверенный вручную акт кладётся в `examples/` парой «страница → правильный
JSON» и подставляется в промпт как образец. Дообучение имеет смысл только
после нескольких сотен размеченных актов.

### Персональные данные

В актах есть ФИО, адреса, телефоны, VIN и госномера. Страницы уходят в
облачный API. Прежде чем гонять это на рабочем потоке, согласуй с
работодателем и проверь договор на обработку персональных данных.
